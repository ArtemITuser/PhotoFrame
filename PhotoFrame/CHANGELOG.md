### MSIX(bundle) — рабочая сборка через Visual Studio 2026 (SDK 19041+)
- **Найдена и исправлена корневая причина** ошибки `Manifest references
  file 'PhotoFrame.exe' which is not part of the payload`: устаревшие цели
  Desktop Bridge (`Microsoft.DesktopBridge.targets`, на которые опирается
  `.wapproj`) не умеют забирать publish-вывод SDK-style проекта — только
  ограниченный набор встроенных build output groups, ни один из которых не
  соответствует self-contained публикации .NET 8. `PhotoFrame.csproj`
  получил именованную цель `__GetPublishItems`
  (`ComputeFilesToPublish`/`ResolvedFileToPublish` — стабильная часть
  публикационного конвейера SDK, задокументированный приём с эпохи
  .NET Core 3.0), а новый `PhotoFrame.Package.wapproj` явно запрашивает её
  через `PackageOutputGroups` и публикует референс ДО сборки пакета.
- `PhotoFrame.csproj`: добавлен `<RuntimeIdentifiers>win-x86;win-x64
  </RuntimeIdentifiers>` (множественное число — обязателен для restore-
  графа, без него передача `RuntimeIdentifier` через `.wapproj` упёрлась бы
  в `NETSDK1047`).
- Добавлены `PhotoFrame.Package.wapproj` (готовый, настроенный проект
  упаковки — раньше `README_MSIX.md` просто описывал, как создать такой
  проект вручную через мастер VS, что и было источником проблемы, поскольку
  мастер генерирует "стандартный", не рассчитанный на self-contained SDK-
  style публикацию `.wapproj`) и `PhotoFrame.sln` (классический формат —
  нужен для корректной работы project-to-project ссылки на `.wapproj`,
  который пока не полностью поддерживается новым `.slnx`).
  `PhotoFrame.slnx` при этом сохранён и упрощён до одного `PhotoFrame.csproj`
  — для повседневной разработки без MSIX открывать по-прежнему можно его.
- Только x86/x64 как реальные, пакуемые в MSIX платформы (не Any CPU — у
  MSIX-пакета должен быть конкретный `ProcessorArchitecture`).
- `.github/workflows/build-release.yml`: добавлен необязательный,
  best-effort job сборки MSIX для CI (`continue-on-error: true`,
  отдельный от InnoSetup/ClickOnce — их публикация НЕ пострадает, если
  этот job когда-либо начнёт падать).
- `Package/README_MSIX.md` переписан: инструкция теперь "откройте
  PhotoFrame.sln и соберите" вместо "создайте проект упаковки заново",
  плюс таблица диагностики типичных ошибок (несовпадение платформ в
  Configuration Manager, NETSDK1047 и т.п.) и честное объяснение, почему
  зависимость на `Microsoft.VCLibs.140.00.UWPDesktop` здесь не объявлена
  по умолчанию (self-contained .NET 8 уже несёт свои копии нужных DLL).

### MTP/PTP-браузер устройств — устройства теперь действительно находятся
- **Главная причина, по которой НИ ОДНО устройство не находилось** (ни
  Lumia 950, ни POCO M8 Pro 5G, ни iPhone 13 mini, ни Coolpix S33) —
  однострочный баг в проверке "это диск, пропускаем": `path[1] == ':'`
  должен был отсекать `C:\`, `D:\` и т.п., но MTP/AFC-устройства отдают
  shell parsing path вида `::{20D04FE0-…}\…` — начинающийся с ДВУХ
  двоеточий, то есть символ [1] там тоже `':'`! Проверка ложно срабатывала
  на КАЖДОМ настоящем устройстве, и все они отбрасывались как "диски" ещё
  до появления в списке. Исправлено: дополнительно требуется, чтобы первый
  символ был буквой (`char.IsLetter(path[0]) && path[1] == ':'`).
- Второй, более ранний фактор (сохранён): COM-перечисление устройств
  теперь выполняется на отдельном потоке с явным `ApartmentState.STA`, а
  не через `Task.Run` (ThreadPool, по умолчанию MTA) — Shell.Application и
  WPD-провайдеры пространства имён документированно менее надёжны на MTA.
- `DeviceKind.Camera` — новый вид устройства (Nikon/Canon/Sony/GoPro/
  Fujifilm/Olympus/Panasonic и т.п. в имени) для более точной иконки;
  список распознаваемых брендов Android/камер расширен.
- Честно задокументировано (README_ANS.md, комментарии в коде): часть
  устройств физически МОГУТ не быть MTP/PTP вообще (простые фотоаппараты
  часто работают как обычный USB Mass Storage — буква диска, "+ Диск", а
  не этот браузер), а iPhone требует установленного Apple Mobile Device
  Support — ни то, ни другое не решается кодом этого приложения.

### Кроссканальное обновление — реальное скачивание и запуск
- Новый `Services/SystemIntegration.Updates.cs`: определяет канал
  установки (`DetectInstallChannel` — MSIX/ClickOnce/InnoSetup/переносная),
  парсит `assets` релиза GitHub через `System.Text.Json` (раньше
  `CheckUpdateAsync` вообще не читал assets — только `tag_name` вручную по
  строке), подбирает подходящий файл под текущую архитектуру ОС.
- Подбор файла: на x86-системе годятся только имена с
  x86/x86-32/x32/anycpu/universal; на x64 сначала ищется x64, при
  отсутствии допустим x86 (WOW64). Если найденный файл — `.zip` (в
  переписке был показан реальный пример: GitHub-вложение
  `PhotoFrame_v1.2.2.0_x86_Setup.zip` — иногда установщик кладут как zip,
  а не голый exe), он распаковывается во временную папку, и уже там
  ищется `.exe`/`.msix`/`.msixbundle`.
- Поведение по каналам — ровно как указано:
  **ClickOnce** обновляется полностью сам, программа только опционально
  "подталкивает" его проверку (`TryNudgeClickOnceUpdateCheck`, best-effort,
  безопасный no-op если недоступно) и ничего не скачивает/не ставит сама.
  **InnoSetup** — скачивает установщик и просто ЗАПУСКАЕТ его (обычный
  `ShellExecute`, без silent-флагов и без принудительного `runas`/UAC —
  установка per-user и не требует прав администратора), дальше пользователь
  ведёт диалог InnoSetup сам, вручную. Постоянный `AppId` в `Installer.iss`
  — уже достаточное условие, чтобы InnoSetup сам корректно обновил
  предыдущую установку поверх, без специальной логики в коде.
  **MSIX** — аналогично InnoSetup: скачивает `.msix`/`.msixbundle` и
  открывает его, что запускает системный App Installer.
- Новая кнопка «⬇ Скачать и установить» в Настройках → Обновления —
  видна только когда действительно найден подходящий файл; перед скачиванием
  всегда явное подтверждение диалогом (ничего не запускается без действия
  пользователя). Прогресс скачивания — с процентом и мегабайтами.
- Баллун в трее при найденном обновлении теперь ведёт в Настройки (сразу к
  кнопке установки), а не просто открывает GitHub; для ClickOnce текст
  баллуна отдельно поясняет, что обновление произойдёт само.

### Слияние веток
Пользователь передал независимо доработанную копию (с изменённым для
личной сборки копирайтом — не перенесён, в остальном код объединён с этой
веткой). Что взято оттуда: указанный выше баг с `path[1] == ':'` для
MTP/AFC-путей (наиболее ценная находка), `DeviceKind.Camera` и расширенный
список брендов, доп. `try/catch` вокруг `LiveTileService.
SetAppUserModelId()` при старте, отображение прогресса скачивания в
процентах/МБ. Что НЕ взято и почему: воскрешённый `Services/
UpdateService.cs` запускал скачанный InnoSetup-установщик с флагами
`/VERYSILENT /SUPPRESSMSGBOXES ... Verb=runas` — полностью автоматическая,
без вывода UI, да ещё и с принудительным запросом прав администратора
установка, что прямо противоречит актуальному пожеланию ("должен просто
запускаться скачанный установщик, а далее ручное обновление") и не
нужно для per-user-установки (`PrivilegesRequired=lowest` в
`Installer.iss`); фильтрация файлов релиза только по `.exe` без учёта zip
и без токенов x86-32/x32/anycpu/universal также уже была шире реализована
в этой ветке. Безусловное `<RuntimeIdentifier Condition="'$(Platform)' ==
'x86'">...` в `PhotoFrame.csproj` не перенесено — не требуется при уже
работающей передаче RID через `.wapproj`, а второй, независимый источник
`RuntimeIdentifier` рядом с уже добавленным `RuntimeIdentifiers` рискует
внести путаницу без явной пользы.

### Live Tiles — реальная причина, по которой плитки не обновлялись
- **Баг**: `LiveTileService.GetUpdater()` запрашивал обновлятель плитки
  через `CreateTileUpdaterForApplication("ArtemITuser.PhotoFrame")` —
  строковый Id. Эта перегрузка предназначена для пакетов с НЕСКОЛЬКИМИ
  `<Application>`-записями и ищет указанный Id именно среди них, а
  `Package.appxmanifest` объявляет `<Application Id="PhotoFrame">` —
  другую строку. Несовпадение → обновление тихо "не находило" своё же
  приложение. Заменено на беспараметрный
  `CreateTileUpdaterForApplication()` ("текущее приложение пакета") —
  корректно работает для пакета с одной Application-записью независимо
  от того, как называется её Id.
- **Баг**: `TryPinTileAsync()` создавал `SecondaryTile` через
  `Activator.CreateInstance` с ошибочными типами аргументов — строка
  там, где конструктору нужен `Uri` логотипа. Reflection не находил
  совпадающий конструктор и падал в `catch` при каждом вызове —
  закрепление плитки не работало никогда, независимо от способа
  установки. Переписано через `SecondaryTile(tileId)` + установку
  свойств (`DisplayName`/`Arguments`/`VisualElements`/`DesiredSize`) по
  отдельности — устойчивее к reflection, чем угадывание сигнатуры
  многоаргументного конструктора.
- **Уточнение**: и обновление плитки, и её закрепление в принципе
  работают только при наличии package identity (MSIX либо sparse-пакет)
  — это ограничение самого Windows, а не этого приложения. Раньше
  `IsPinningSupported()` проверял только наличие WinRT-типов в системе
  (доступны на любой Windows 10/11 независимо от identity), поэтому
  кнопка закрепления показывалась и там, где закрепить было физически
  невозможно — ClickOnce и InnoSetup НЕ дают package identity. Теперь
  дополнительно проверяется `SystemIntegration.IsRunningAsMsixPackage()`
  — кнопка и текст в разделе Live Tiles показывают реальную доступность.
- **Критический баг сборки**: в незакоммиченной копии проекта
  (`PhotoFrame.csproj`) `WindowsPackageType=MSIX` и `EnableMsixTooling`
  были включены БЕЗ УСЛОВИЯ — это заставляло абсолютно любую сборку
  (включая обычный `dotnet build` и Release-публикацию для InnoSetup)
  требовать `Package.appxmanifest` и `Images\*.png` по путям, которых в
  проекте нет (реальные пути — `Package\Package.appxmanifest` и
  `Package\Assets\*.png`). Однопроектный MSIX-инструментарий убран из
  сборки по умолчанию — рабочий, уже задокументированный способ собрать
  MSIX остаётся прежним, отдельный проект упаковки
  (`Package\Package.appxmanifest`, см. `Package\README_MSIX.md`).
- Удалён второй, битый манифест в корне проекта
  (`package.appxmanifest`, со строчной "p") — черновик от того же
  незавершённого эксперимента, с недействительными пространствами имён
  (`http://microsoft.com` вместо `http://schemas.microsoft.com/...`),
  без `<Identity>` и с неподставленным `$targetnametoken$.exe`. Второго
  манифеста в проекте больше нет — единственный используемый:
  `Package\Package.appxmanifest`.
- `AppSettings.LiveTilesLargeEnabled` существовал, но ни разу не
  читался и не записывался — настройка была "мёртвой". Теперь реально
  исключает биндинг `TileLarge` при обновлении плитки, если выключена;
  добавлен флажок в разделе Live Tiles (было невозможно выключить
  крупную плитку из интерфейса вообще).
- Формулировка "(только ClickOnce)" у флажка обновления плитки была
  неточной — заменена на пояснение про MSIX/package identity (см. выше).

### Иерархический просмотр USB-устройств (Lumia / Android / iOS) — исправлено
- **Баг**: выбор ВЛОЖЕННОЙ папки устройства (глубже первого уровня)
  резолвился повторным вызовом `shell.NameSpace(node.ShellPath)`, где
  `ShellPath` — это `FolderItem.Path` вложенного MTP-элемента. Для MTP
  такое значение хорошо известно как ненадёжное на глубине больше
  одного уровня — `NameSpace()` рассчитан на файловые пути и известные
  корни, а не на произвольные внутренние пути виртуального MTP-
  пространства имён. На практике это означало, что подсчёт фото и
  импорт из папки типа «Телефон → DCIM → Camera» мог не находить ничего
  или (реже) резолвиться не в ту папку.
- **Ограничение**: дерево строилось ЖАДНО и только на фиксированную
  глубину 3 уровня (`GetDeviceTree(device, maxDepth: 3)`) — меньше, чем
  типичная вложенность реальных телефонов (например, iOS: `Internal
  Storage\DCIM\100APPLE` — уже 3 уровня ДО самих файлов; Android с
  папками WhatsApp/Screenshots и т.п. нередко глубже).
- **Исправлено**: `DeviceBrowserService` переписан — каждый `DeviceNode`
  хранит ссылку на корневой узел устройства и путь ИМЁН папок от корня
  до себя. Любая операция с вложенной папкой резолвится ОДНИМ надёжным
  `NameSpace()` на корне устройства (доказанно работает — так строится
  сам путь пользователя из "Этот компьютер") плюс пошаговым обходом
  `.Items()`/`.GetFolder` по сохранённым именам — тем же приёмом, каким
  строилось дерево. Дерево теперь раскрывается ЛЕНИВО на каждом уровне
  (а не только на верхнем, как раньше) — ограничения глубины больше
  нет, работает как обычный проводник для флешки, чего и просили.
- Добавлена защита от зависания: блокирующие COM-вызовы перечисления
  устройств/папок оборачиваются в таймаут (15 с) на отдельном потоке —
  "уснувшее"/не отвечающее устройство больше не подвешивает окно
  браузера устройств насовсем (сам поток может продолжать ждать нативный
  вызов — это ограничение позднего связывания COM, а не утечка; поток
  завершится сам, если/когда вызов вернёт управление).
- Доп. фильтр ложных срабатываний: элементы "Этот компьютер" с
  `IsFileSystem = true` (но без буквы диска) больше не считаются
  кандидатами в устройства.
- Значок «Обновить» в разделе импорта с телефона (уже был поправлен на
  раздельные `TextBlock` для глифа/текста) — снята жёсткая `Height="13"`,
  которая могла обрезать сам глиф; теперь `FontSize`+`VerticalAlignment`,
  как и остальные MDL2-иконки в приложении.

### COMException / UCEERR_RENDERTHREADFAILURE — причина найдена
- Диалог `"Ошибка: UCEERR_RENDERTHREADFAILURE (0x88980406) / Тип:
  COMException"` — это УЖЕ перехваченное исключение: в
  `App.xaml.cs` давно существует `DispatcherUnhandledException`,
  которая перехватывает и показывает ЛЮБОЕ исключение диспетчера,
  включая это. Приложение не падало (процесс оставался жив — это видно
  и на скриншоте диспетчера задач), но пугало техническим кодом ошибки
  в ситуации, которая почти всегда самоустраняется без вмешательства:
  `UCEERR_RENDERTHREADFAILURE` — сбой потока композиции WPF, который
  типично возникает сразу после выхода из спящего режима или сброса
  видеодрайвера, и WPF в большинстве случаев пересоздаёт поток
  композиции сам.
- **Исправлено**: этот конкретный HRESULT теперь распознаётся отдельно
  и подавляется без показа диалога (только запись в Trace для
  диагностики). Остальные исключения по-прежнему показываются, но не
  чаще одного диалога раз в 5 секунд — всплеск из нескольких исключений
  подряд больше не заваливает пользователя стопкой модальных окон.
- Добавлены `AppDomain.UnhandledException` и
  `TaskScheduler.UnobservedTaskException` как страховочные обработчики
  для исключений вне UI-потока — раньше такое ничем не логировалось
  перед завершением процесса.

### Сон / пробуждение — сохранение состояния
- Обработчик `SystemEvents.PowerModeChanged` (подписка в `OnLoaded`,
  симметричная отписка в `OnClosing` — по той же схеме, что уже
  использовалась для `App.ThemeChanged`, во избежание утечки через
  статический источник событий). При уходе в сон текущее состояние
  (полноэкранный режим, воспроизведение) сохраняется на диск; при
  пробуждении визуальный слой "подталкивается" через небольшую паузу и
  `InvalidateVisual()` — дополнительная подстраховка к обработке
  COMException выше, а не замена ей.
- Новые настройки: `RestoreLastSessionState` (флажок «Восстанавливать
  полноэкранный режим и воспроизведение после сна/перезапуска» —
  раздел «Основное», по умолчанию включено), `WasFullscreen`,
  `WasPlaying`. При следующем запуске, если были активны в прошлом
  сеансе, полноэкранный режим и слайд-шоу восстанавливаются
  автоматически (слайд-шоу — один раз, сразу после старта; не
  переоткрывается при последующих пересканированиях в течение того же
  сеанса, чтобы не сбрасывать намеренную паузу пользователя).

### USB-флешки — без "постфактум" ошибок
- **Баг**: любой отсутствующий путь-источник (включая просто не
  воткнутую в данный момент USB-флешку — штатная ситуация) немедленно
  порождал баннер «Путь недоступен», часто заметно позже самого
  отключения — при следующем пересканировании (открытие настроек,
  перезапуск и т.п.).
- **Исправлено**: пути, добавленные со съёмных носителей
  (`AppSettings.RemovableSourcePaths` — определяется по `DriveType` в
  момент добавления, автоматически для предложенных при подключении
  флешек и по явному выбору в разделе «+ Диск»), при временном
  отсутствии теперь тихо пропускаются сканером вместо показа ошибки —
  путь остаётся в источниках и сам "оживёт", когда накопитель окажется
  на месте. Обычные (несъёмные) пути по-прежнему считаются ошибкой при
  отсутствии — это по-прежнему полезный сигнал для внутреннего тома или
  сетевого диска.

### Совместимость с x86 (x32)
- **Баг**: единственный реально используемый publish-профиль
  (`FolderProfile1.pubxml`, х86, self-contained) включал
  `PublishTrimmed=true`. Microsoft прямо документирует WPF как НЕ
  безопасный для trimming (интенсивная reflection в системе XAML/
  стилей/биндингов) — вместе с уже имеющимся в этом проекте `dynamic`
  COM-взаимодействием (`DeviceBrowserService`) и WinRT-reflection
  (`LiveTileService`) это реальный источник трудновоспроизводимых
  падений, которые проявляются только в Release-публикации и не
  ловятся в Debug. Отключено (`PublishTrimmed=false`).
- Профили публикации приведены в порядок: удалён `FolderProfile.pubxml`
  (на самом деле — устаревшая копия ClickOnce-профиля с версией
  1.2.0.3, ошибочно занимавшая имя "Folder"), удалён задвоенный
  `FolderProfile1.pubxml`. Добавлены явно поименованные
  `FolderProfile.x86.pubxml` и `FolderProfile.x64.pubxml` — оба
  self-contained, single-file, ReadyToRun, БЕЗ trimming.
- `Installer.iss` теперь параметризован по архитектуре
  (`iscc "/DAppArch=x64" Installer.iss"`, по умолчанию x86 — x86-сборка
  запускается и на x86, и на x64 Windows через WOW64, поэтому остаётся
  "универсальным" вариантом по умолчанию). Убрана проверка "не найден
  .NET Desktop Runtime" — публикация self-contained, рантайм не нужен,
  а старая проверка либо ничего не давала, либо могла показать лишний
  всплывающий диалог там, где он не нужен.
- `.github/workflows/build-release.yml`: исправлено расхождение путей
  публикации — CI публиковал `-r win-x64 --self-contained false -o

  `bin\Release\net8.0-windows10.0.19041.0\publish\` — другой путь;
  последовательный запуск в CI собрал бы установщик из пустой или
  устаревшей папки. Теперь публикация идёт через те же
  `FolderProfile.x86`/`.x64` профили, что и локально, сборка и загрузка
  установщиков для обеих архитектур отдельными джобами. Заодно
  поправлен плейсхолдер `<user>.github.io` → `artemituser.github.io`.
- P/Invoke-сигнатуры в `SystemIntegration.cs` проверены на корректность
  типов под x86/x64 (использование `IntPtr`/`nint` для хэндлов и
  указателей) — проблем не найдено, изменений не потребовалось.

### Автозагрузка и регистрация скринсейвера — корректный EXE + обработчики ошибок
- **Баг**: `SetAutostart` использовал
  `Assembly.GetExecutingAssembly().Location` — для однофайловой
  (`PublishSingleFile`) публикации это пустая строка, а для обычной
  публикации .NET 5+ указывает на управляемую `.dll`, а не на apphost
  `.exe` (Windows не может запустить `.dll` через `ShellExecute`). Для
  ClickOnce дополнительно — путь к `.exe` меняется при КАЖДОМ
  автообновлении (версионированный кеш-каталог), поэтому ранее записанный
  путь в `HKCU\Run` неизбежно ломался после следующего обновления.
- **Исправление**: `ResolveHostExecutablePath()` — для ClickOnce ищет
  стабильный ярлык `*.appref-ms` в Меню Пуск (ClickOnce сам поддерживает
  его актуальным), иначе использует `Environment.ProcessPath` (корректно
  работает для single-file/self-contained/framework-dependent публикации).
- **MSIX**: автозапуск для MSIX-пакета объявляется в
  `Package.appxmanifest` (`windows.startupTask`) — при обнаружении
  package identity (`GetCurrentPackageFullName`) `SetAutostart` больше не
  трогает реестр и сообщает пользователю о правильном месте включения
  (Диспетчер задач → «Автозагрузка»).
- **Обработчики ошибок** добавлены во все точки: `SetAutostart` и
  `RegisterScreensaver` теперь возвращают конкретную причину отказа
  (`UnauthorizedAccessException`, `SecurityException`, занятый файл,
  недоступный раздел реестра) вместо молчаливого проглатывания —
  `OnApply` в настройках показывает ошибку автозагрузки пользователю.
- Три места `new HttpClient(...)` в `SystemIntegration` заменены на общий
  статический клиент ещё в build 51 — здесь дополнительно ревизия
  подтвердила отсутствие регрессий.
