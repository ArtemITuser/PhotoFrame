build 56: рабочая сборка MSIX(bundle) через `PhotoFrame.Package.wapproj`
(была документацией "как создать вручную" — стала готовым, настроенным

диск"), кроссканальная система обновления с реальным скачиванием и

исключением явно помеченных build 56 изменений.

## 1. ClickOnce vs InnoSetup — рекомендации по упаковке

### Текущая схема (ClickOnce)

ClickOnce остаётся основным каналом распространения:

- **Установка без прав администратора** — разворачивается в
  `%LocalAppData%\Apps\2.0\...`, не требует UAC при первой установке.
- **Автообновление** — при каждом запуске проверяется манифест на
  сервере/gh-pages; при наличии новой версии — тихое обновление в фоне.
- **Подходит для однопользовательских ПК/ноутбуков**, где рамка запускается
  под тем же профилем Windows, что и был при установке.

### Когда добавить InnoSetup параллельно

InnoSetup — не замена ClickOnce, а **дополнительный канал** для сценариев,
которые ClickOnce не покрывает:

| Сценарий | Почему нужен InnoSetup |
|---|---|
| Регистрация скринсейвера (`.scr` в `System32`) | ClickOnce не даёт доступа к системным папкам вне песочницы приложения; сейчас это решается через `SystemIntegration.ElevatedCopy()` (UAC на лету), но встроенная в инсталлятор регистрация надёжнее |
| Установка на все профили компьютера (не только текущий пользователь) | ClickOnce — всегда per-user |
| Оффлайн/портативная установка без интернета | ClickOnce требует доступности манифеста при первом запуске |
| Кастомная логика деинсталляции (например, откат HKCU\Run, HKCU\Control Panel\Desktop) | `[UninstallRun]`/`[UninstallDelete]` в `.iss` дают точный контроль |

**Рекомендация:** оставить ClickOnce как основной путь для большинства
пользователей; предлагать `.exe`-инсталлятор (InnoSetup) как «Portable /
offline install» на странице релизов GitHub — оба артефакта собираются
одним пайплайном GitHub Actions (`.github/workflows/build-release.yml`)
и публикуются в одном Release, не конфликтуя друг с другом. Скрипт
инсталлятора — `Installer.iss` в корне проекта.

### Зеркало / своя ссылка для проверки обновлений (новое в build 52)

Добавлено поле **Настройки → О программе → «Зеркало / своя ссылка»**.
Реализация — `SystemIntegration.CheckUpdateAsync(Version current, string?
customUrl)`:

- Пусто (по умолчанию) → официальный `api.github.com/repos/.../releases/latest`
- Заполнено → GET-запрос на указанный URL; ожидается тот же JSON-формат,
  что отдаёт GitHub Releases API (поле `"tag_name"`)

Это позволяет:
1. Указать региональное зеркало GitHub API (для сетей с ограниченным доступом).
2. Развернуть собственный лёгкий эндпоинт (например, статический JSON-файл
   на любом хостинге), который отдаёт `{"tag_name": "v1.4.0.1"}` — без
   необходимости поднимать полноценный GitHub-совместимый сервер.

Метод `CheckGitHubUpdateAsync` сохранён для обратной совместимости и
вызывает `CheckUpdateAsync(cur, null)`.

## 2. Что переделано при откате к b46 → build 52

### 2.1 Исправления (повторно применены после отката)

- **P/Invoke**: все `[DllImport]` в `SystemIntegration.cs` переведены на
  `[LibraryImport]` (`static partial class` + `partial` методы) —
  устраняет info-сообщения VS2026 про рантайм-маршалинг.
- **`PreventSleep`**: возвращает `bool`, реально проверяя ненулевой
  результат `SetThreadExecutionState`, а не игнорируя его.
- **`.csproj`**: добавлен `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>`
  (требуется для `LibraryImport` source-generator) и пакет
  `Microsoft.CSharp` (нужен для `dynamic` в `DeviceBrowserService`).

### 2.2 Win7/8 — шрифт значков

`SystemIntegration.ShouldOfferMdl2Font()` возвращает `true`, только если:
`Environment.OSVersion.Version.Major < 10` **и** шрифт физически
отсутствует в `HKLM\...\CurrentVersion\Fonts` **и** пользователь не
отказался навсегда (`HKCU\Software\PhotoFrame\Mdl2FontDeclined`).

На Windows 10/11 первое условие всегда `false` — диалог не показывается
никогда, без дополнительных проверок в UI-коде.

Установка — временный `.cmd` с `copy` в `%windir%\Fonts` и `reg add` в
`HKLM\...\CurrentVersion\Fonts`, запущенный через `Verb=runas` (единый
UAC-промпт вместо двух отдельных операций).

### 2.3 Стоп-лист недоступных путей

`OnCloseDiskError` (крестик) добавляет путь в
`HKCU\Software\PhotoFrame\DismissedPaths` (список через `|`). При
следующем сканировании `ReloadPhotosAsync` фильтрует `DiskErrors` через
`_dismissedPaths.Contains(err.Path)` — баннер для уже закрытых путей не
появляется повторно.

`OnRemoveErrorPath` («Удалить из списка») — путь удаляется из
`SelectedPaths` **и** из стоп-листа (если диск/путь добавят снова вручную,
ошибка должна показаться заново).

### 2.4 О программе — память и кеш

`SystemIntegration.GetMemoryUsageInfo()` возвращает `WorkingSet64`,
`PrivateMemorySize64`, `GC.GetTotalMemory()`, и размер/количество файлов в
`%TEMP%\PhotoFrameCache`. Кнопка «Безопасная очистка» вызывает
`SafeCleanup()`: `GC.Collect(2, Forced, blocking:true, compacting:true)` +
`GCSettings.LargeObjectHeapCompactionMode = CompactOnce`, затем удаление
файлов кеша превью.

### 2.5 Живые плитки

- Частота обновления картинки — независимый слайдер (0–120 сек, 0 = как
  слайдшоу), хранится в `AppSettings.LiveTileCycleIntervalSeconds`.
  `ShowCurrentAsync` throttle-ит вызов `LiveTileService.UpdateTile()` по
  `_lastTileUpdateUtc`.
- Кнопка «Закрепить плитку» — `LiveTileService.TryPinTileAsync()` через
  `Windows.UI.StartScreen.SecondaryTile` (WinRT-рефлексия, без прямой
  зависимости от Windows SDK в `.csproj`). Видна только если
  `IsPinningSupported()` истинно.

**build 53 — почему плитки на самом деле не обновлялись/не закреплялись:**
Дело было не в правах или регистрации, а в двух конкретных багах кода:

1. `GetUpdater()` запрашивал `CreateTileUpdaterForApplication(AppId)` со
   строкой `"ArtemITuser.PhotoFrame"`, а `Package.appxmanifest` объявляет
   `<Application Id="PhotoFrame">` — другая строка. Эта перегрузка API
   ищет Id ИМЕННО среди `<Application>`-записей пакета (сценарий
   "несколько exe в одном пакете"), поэтому при несовпадении просто не
   находила "своё" приложение. Заменено на беспараметрный
   `CreateTileUpdaterForApplication()` — не зависит от строки Id вообще.
2. `TryPinTileAsync()` создавал `SecondaryTile` через
   `Activator.CreateInstance(t, AppId, "PhotoFrame", "photoframe-tile",
   AppId, ...)` — четвёртым параметром передавалась СТРОКА, хотя
   конструктор `SecondaryTile(tileId, displayName, arguments,
   square150x150Logo, desiredSize)` ожидает там `Uri` логотипа.
   Reflection не находит перегрузку конструктора по несовпадающим
   типам аргументов → `Activator.CreateInstance` бросает исключение,
   перехватываемое `catch` — метод всегда молча возвращал `false`.
   Переписано через `SecondaryTile(tileId)` + раздельную установку
   свойств (`DisplayName`, `Arguments`, `VisualElements.
   Square150x150Logo` и т.д., `DesiredSize`) — не зависит от точной
   сигнатуры многоаргументного конструктора.

Оба API дополнительно **требуют package identity** (MSIX или sparse-
пакет) само по себе — это ограничение Windows, не приложения. Ни
ClickOnce, ни InnoSetup identity не дают. `IsPinningSupported()` теперь
проверяет `SystemIntegration.IsRunningAsMsixPackage()` в дополнение к
наличию WinRT-типов (те резолвятся в ОС независимо от identity — раньше
кнопка закрепления показывалась и там, где не могла сработать).
`AppSettings.LiveTilesLargeEnabled` (существовал, но не был подключён ни
к UI, ни к `UpdateInternal`) теперь реально исключает биндинг
`TileLarge`, когда выключен — флажок добавлен в Настройки.

### 2.6 Скринсейвер — исправлена логика запуска из трея

Новый `_idleCheckTimer` (интервал 20 сек) в `MainWindow` проверяет
`SystemIntegration.IsSystemIdle(TimeSpan)` — обёртку над `GetLastInputInfo`
(**системный**, не оконный простой: клавиатура/мышь/тач по всей ОС).
Полноэкранный показ запускается, только если:

1. Окно скрыто в трей (`Visibility == Hidden`, а не просто `Minimized`).
2. `ScreensaverDelayMinutes > 0`.
3. Система реально простаивает ≥ этого порога.

Это отдельно от **системной** регистрации `.scr` (та продолжает работать
как раньше через `RegisterScreensaver`/`Control Panel\Desktop`).

### 2.7 Автоотключение рамки по расписанию (новое)

`Services/AutoOffScheduler.cs` — три независимых режима
(`AppSettings.AutoOffMode`):

| Режим | Логика |
|---|---|
| `SmartUsage` | Скользящее окно 4 часа: если система была активна < 15% времени — считаем "нерабочим" временем, сворачиваем |
| `ManualSchedule` | Простое "с ЧЧ:ММ до ЧЧ:ММ" (`AutoOffFromMinutes`/`AutoOffToMinutes`), поддерживает переход через полночь |
| `SunsetToSunrise` | `SystemIntegration.CalculateSunTimes()` — упрощённая формула NOAA (без интернета); координаты — вручную или через `TryGetApproxLocationAsync()` (ip-api.com, кеш 12ч) |

Не путать с системным скринсейвером/питанием — `AutoOffScheduler` просто
скрывает/показывает окно PhotoFrame (`Hide()`/`Show()`), не трогая
настройки Windows.

### 2.8 Просмотр USB-устройств (Lumia/Android/iOS)

`Services/DeviceBrowserService.cs` + `Views/DeviceBrowserWindow.xaml(.cs)`.

Технически: устройства без буквы диска под "Этот компьютер" видны только
через `Shell.Application` COM (`Windows.Storage`/MTP API в WPF/.NET 8 без
UWP-упаковки не тривиален). Используется позднее связывание (`dynamic`,
`Type.GetTypeFromProgID`) — не требует COM-референса в `.csproj`, только
пакет `Microsoft.CSharp` для поддержки `dynamic`.

Импорт копирует файлы через `Shell.Folder.CopyHere()` в
`%LocalAppData%\PhotoFrame\DeviceImports\{Устройство}\`, после чего этот
путь добавляется в `SelectedPaths` как обычная папка — `FileScanner`
работает с ним без изменений.

**Ограничение**: `CopyHere` — асинхронная shell-операция без промиса;
используется поллинг количества файлов (таймаут 5 минут).

**build 56 — настоящая причина, по которой устройства вообще не находились:**
Фильтр "пропустить, если это буква диска" в `GetConnectedDevices` проверял
`path.Length >= 2 && path[1] == ':'`, рассчитывая отсечь `C:\`, `D:\` и
т.п. Но MTP/AFC-устройства (телефоны, некоторые камеры) отдают через
`FolderItem.Path` не файловый путь, а shell "parsing path" вида
`::{20D04FE0-3AEA-1069-…}\…` — строку, НАЧИНАЮЩУЮСЯ С ДВУХ ДВОЕТОЧИЙ, то
есть символ с индексом [1] там ТОЖЕ `':'`! Проверка ложно срабатывала на
КАЖДОМ настоящем устройстве, и все они отбрасывались как "диски" ещё до
того, как попасть в список — то есть баг был не в глубине дерева или в
резолвинге вложенных папок (см. build 53 ниже), а на самом первом шаге,
до которого остальная логика файла вообще не успевала дойти. Исправлено:
дополнительно требуется, чтобы ПЕРВЫЙ символ пути был буквой
(`char.IsLetter(path[0]) && path[1] == ':'`) — так по-прежнему отсекаются
именно буквы дисков, но не строки, начинающиеся с двоеточия по другой
причине.

**build 53 — переход на резолвинг по пути имён, не по строке пути:**
`FolderItem.Path` для ВЛОЖЕННЫХ MTP-элементов — известно ненадёжное
значение для повторного резолвинга через `shell.NameSpace(path)` (тот
рассчитан на файловые пути и известные корни, а не на произвольные
внутренние пути виртуального MTP-пространства имён). Раньше
`EstimatePhotoCount`/`ImportPhotosAsync` резолвили выбранную папку
именно так — работало для папки первого уровня (устройство), могло не
работать для вложенной. Плюс дерево строилось жадно и на фиксированную
глубину 3 (`GetDeviceTree(device, maxDepth: 3)`).

Теперь `DeviceNode` хранит ссылку на узел устройства (`RootDevice`) и
путь ИМЁН папок от него (`NamePath`). Любая операция с вложенным узлом
резолвит `NameSpace()` только ОДИН раз — на пути устройства верхнего
уровня (доказанно надёжно — так пользователь и дошёл до узла из "Этот
компьютер"), а дальше идёт пошаговым обходом `.Items()`/`.GetFolder` по
сохранённым именам, тем же способом, каким строится дерево. Дерево
теперь раскрывается лениво на КАЖДОМ уровне (`GetChildren` — один
уровень за раз, вызывается заново при каждом реальном `Expanded`), а не
только на верхнем как раньше — ограничения глубины больше нет.

Добавлен таймаут (15 с, `RunBlocking<T>`) вокруг блокирующих COM-вызовов
перечисления — не отвечающее устройство больше не подвешивает окно
браузера насовсем (сам поток не отменяется — позднее связывание COM не
поддерживает отмену на уровне ОС, — но управление возвращается
вызывающей стороне).

### 2.9 GPS → название места на русском

`Services/ReverseGeocodeService.cs` — OpenStreetMap Nominatim, без ключа,
rate-limit 1 запрос/сек (политика Nominatim), кеш в памяти по округлённым
координатам. Опция **Настройки → Наложения → «Определять название места
через интернет»** (`AppSettings.GpsReverseGeocodeEnabled`, по умолчанию
выключено — без согласия пользователя сетевые запросы не выполняются).

### 2.10 Баг: счётчик кадров показывал неверную позицию

`PlaylistManager.CurrentIndex` возвращал индекс в **исходном** списке
фотографий (`_source`), а не позицию в **очереди воспроизведения**
(`_order`). В режимах `Shuffle`/`TrueRandom` счётчик "N / всего" в
интерфейсе показывал случайное число, не совпадающее с реальным порядком
показа, а проверки "это первое/последнее фото" (`Start`/`EndUnavailable`
иконки) срабатывали неправильно.

**Исправление**: добавлены `PlaybackPosition` (0-based позиция в очереди),
`IsAtStart`, `IsAtEnd` — используются в `SyncCounter()` и
`ApplyToolbarIcons()` вместо `CurrentIndex`. `CurrentIndex` сохранён для
`JumpToSource()` (не изменяет публичный контракт).

### 2.11 Центрирование тулбара

Блок навигации (Назад/Play/Вперёд) был `Grid.Column="1"` внутри
трёхколоночного `Grid` — центрировался только относительно средней "*"
колонки. Левая группа (PlayMode + интервал, ≈194px) и правая (Тема +
Настройки + Полный экран, ≈168px) не равны по ширине → визуальное смещение
≈13px от истинного центра окна.

**Исправление**: `Grid.Column="0" Grid.ColumnSpan="3" Panel.ZIndex="1"` —
блок теперь центрируется относительно всей ширины тулбара независимо от
асимметрии боковых групп.

### 2.12 Иконки экспорта (список/CSV)

Было: `&#xE896;` (Download — семантически неверно для «список файлов») и
`&#xE8A1;` (нечёткий смысл для CSV). Заменены на `&#xE8E5;` (документ со
строками — список) и `&#xE9D9;` (таблица/сетка — CSV).

## 3. Build 53 — сон/пробуждение, COMException, USB-флешки, x86, touch

### 3.1 Причина COMException (UCEERR_RENDERTHREADFAILURE)

Диалог `"Ошибка: UCEERR_RENDERTHREADFAILURE (0x88980406) / Тип:
COMException"` — это уже перехваченное исключение: `App.xaml.cs`
подписан на `DispatcherUnhandledException` и показывал диалог для
ЛЮБОГО исключения диспетчера. Процесс не падал (см. скриншот Диспетчера
задач — PhotoFrame оставался в списке процессов), просто пугал сырым
кодом ошибки в ситуации, которая почти всегда самоустраняется:
`UCEERR_RENDERTHREADFAILURE` — сбой потока композиции WPF, типично
возникающий сразу после выхода из спящего режима или сброса
видеодрайвера; WPF в большинстве случаев пересоздаёт поток композиции
сам, без вмешательства приложения.

Теперь этот конкретный HRESULT распознаётся отдельно
(`App.xaml.cs::OnDispatcherUnhandledException`) и подавляется без
диалога — только `Trace.WriteLine` для диагностики. Остальные диалоги
показываются не чаще одного раза в 5 секунд.

### 3.2 Сон / пробуждение

`MainWindow` подписывается на `Microsoft.Win32.SystemEvents.
PowerModeChanged` в `OnLoaded`, отписывается симметрично в `OnClosing`
(по той же схеме, что уже применялась для `App.ThemeChanged`, — иначе
статический источник событий держал бы окно живым до выхода из
процесса). При `PowerModes.Suspend` текущее состояние
(`_cfg.WasFullscreen`, `_cfg.WasPlaying`) сохраняется на диск; при
`PowerModes.Resume` — небольшая пауза (1.2 с) и `InvalidateVisual()` на
UI-потоке, снижающие (не гарантированно исключающие) шанс поймать
транзиентный сбой композиции сразу после пробуждения.

Новая настройка `AppSettings.RestoreLastSessionState` (по умолчанию
включена, флажок в разделе «Основное»): при следующем запуске, если
`WasFullscreen`/`WasPlaying` были `true` в момент последнего сохранения,
полноэкранный режим и слайд-шоу восстанавливаются автоматически. Это
подстраховка на случай, если процесс всё же не переживёт переход (сам
сон Windows обычно просто приостанавливает процесс — состояние в
памяти переживает его без вмешательства).

### 3.3 USB-флешки — без ошибок постфактум

`AppSettings.RemovableSourcePaths` — подмножество `SelectedPaths`,
помеченное как съёмный носитель в момент добавления (по `DriveInfo.
DriveType == Removable`): автоматически для предложенных при
подключении флешек (`MainWindow.OnDriveInserted`) и по явному выбору в
разделе «+ Диск» (`SettingsWindow.FillDriveButtons`/`OnAddDrive`).
`FileScanner.ScanAsync(..., removableRoots)` тихо пропускает такие пути,
если они временно отсутствуют, вместо создания `DiskError` — путь
остаётся в источниках и сам "оживает" при следующем сканировании после
подключения. Тег снимается только при полном удалении пути из
источников (`OnRemovePath`/удаление через баннер ошибки).

### 3.4 x86 / x64

Единственный реально использовавшийся publish-профиль
(бывший `FolderProfile1.pubxml`) включал `PublishTrimmed=true` —
Microsoft прямо документирует WPF как небезопасный для trimming
(reflection в системе XAML/стилей/биндингов), а этот проект
дополнительно использует `dynamic` COM (`DeviceBrowserService`) и
WinRT-reflection (`LiveTileService`) — реальный риск падений, которые
проявляются только в Release и не ловятся в Debug. Отключено.

Профили переименованы в явные `FolderProfile.x86.pubxml` /
`FolderProfile.x64.pubxml` (оба self-contained, single-file,
ReadyToRun, без trimming). `Installer.iss` параметризован по
архитектуре (`iscc "/DAppArch=x64" Installer.iss"`, x86 по умолчанию —
запускается и на x86, и на x64 Windows через WOW64).
`.github/workflows/build-release.yml` публикует и упаковывает обе
архитектуры отдельными джобами, используя те же profile-файлы, что и
локальная сборка (раньше CI и `Installer.iss` расходились в путях
публикации — см. `CHANGELOG.md`).

### 3.5 Touch-friendly аудит

- `Slider`: увеличенный `Thumb` (16px в покое / 20px при перетаскивании
  + увеличенная зона захвата) — неявный стиль, не затрагивает уже
  стилизованные бегунки `ScrollBar`.
- Подписи под кнопками тулбара (`HoverLabel`) раскрываются также по
  `IsPressed`, не только по `IsMouseOver` — на чистом тач-вводе
  устойчивого "наведения" обычно не возникает.
- Слайдеры «Размер шрифта», «Длительность перехода», «Частота смены
  фото на плитке» получили пару Slider+TextBox (как уже было у времени
  скринсейвера/выключения монитора в build 52) — раньше значение
  менялось только перетаскиванием.

## 4. Build 56 — MSIX(bundle), кроссканальные обновления

### 4.1 MSIX: причина ошибки payload и рабочий вариант

Раньше `Package/README_MSIX.md` только ОПИСЫВАЛ, как создать проект
упаковки (`.wapproj`) вручную через мастер Visual Studio. Проблема была
именно в этом: мастер генерирует "стандартный" `.wapproj`, рассчитанный на
классические .NET Framework/UWP-проекты — а `Microsoft.DesktopBridge.
targets`, на которые он опирается, не умеют забирать publish- (только
build-) вывод SDK-style self-contained проекта. Результат — манифест
пакета ссылается на `PhotoFrame.exe`, который физически никогда не
копируется туда, откуда `.wapproj` его ждёт:
`Manifest references file 'PhotoFrame.exe' which is not part of the payload`.

Исправление — задокументированный с эпохи .NET Core 3.0 приём (актуальный
и для .NET 8, судя по независимым разборам той же ошибки на современных
проектах): `PhotoFrame.csproj` объявляет именованную MSBuild-цель
`__GetPublishItems`, отдающую именно файлы публикации
(`ComputeFilesToPublish`/`ResolvedFileToPublish`); `PhotoFrame.Package.
wapproj` (теперь — готовый, настроенный файл в составе проекта, а не
что-то, что нужно создавать заново) явно запрашивает эту output group
через `PackageOutputGroups` и публикует референс ДО сборки пакета.
`PhotoFrame.csproj` также получил `<RuntimeIdentifiers>win-x86;win-x64
</RuntimeIdentifiers>` (множественное число) — без него передача
`RuntimeIdentifier` через `.wapproj`/`ProjectReference` упёрлась бы в
`NETSDK1047` (assets file не содержит нужного RID, т.к. восстановление
пакетов не подготовило его заранее).

`PhotoFrame.sln` (классический формат) добавлен специально для этого —
project-to-project ссылка на `.wapproj` пока не полностью проверена с
современным `.slnx`. `PhotoFrame.slnx` при этом НЕ убран — упрощён до
одного `PhotoFrame.csproj`, для повседневной разработки без MSIX его
по-прежнему достаточно.

MSIX остаётся ДОПОЛНИТЕЛЬНЫМ, необязательным каналом — ClickOnce и
InnoSetup работают в точности как раньше, ничего не заменено.

### 4.2 Кроссканальные обновления

`Services/SystemIntegration.Updates.cs` (новый файл). Раньше
`CheckUpdateAsync` сравнивал только номер версии (`tag_name`), не читая
`assets` релиза вообще — скачать/поставить обновление было нечем.

- `DetectInstallChannel()` — MSIX (`IsRunningAsMsixPackage`), ClickOnce
  (`IsClickOnceDeployed`), InnoSetup (по ключу реестра деинсталляции
  `HKCU\...\Uninstall\{AppId с Installer.iss}_is1` — установка per-user,
  поэтому HKCU, не HKLM), либо переносная/неизвестная.
- `CheckUpdateWithAssetAsync` — парсит `assets[].name`/
  `assets[].browser_download_url` через `System.Text.Json`, подбирает файл
  под архитектуру ОС: на x86 годятся только имена с
  x86/x86-32/x32/anycpu/universal; на x64 сначала ищется x64, при
  отсутствии допустим x86 (работает через WOW64).
- `DownloadAndLaunchUpdateAsync` — скачивает (с прогрессом в % и МБ),
  распаковывает, если это `.zip` (подтверждённый реальный пример:
  GitHub-вложение может быть заархивировано, не только голый `.exe`), и
  просто ЗАПУСКАЕТ найденный `.exe`/`.msix`/`.msixbundle` через
  `ShellExecute` — без silent-флагов, без принудительного `Verb=runas`
  (установка per-user, права администратора не нужны). Дальше пользователь
  ведёт диалог инсталлятора сам, вручную — программа не автоматизирует сам
  процесс установки, только доводит до момента, когда он уже открыт.
- Постоянный `AppId` в `Installer.iss` — уже достаточное условие для
  корректного обновления поверх старой версии силами самого InnoSetup;
  никакой отдельной логики "найти и удалить старую версию" в коде нет и
  не требуется.
- ClickOnce обновляется полностью на своей стороне — код только
  опционально пытается "подтолкнуть" проверку через устаревший
  `System.Deployment.Application` API (доступен только под .NET Framework,
  почти наверняка недоступен на .NET 8 — вызов через reflection с
  безопасным no-op, если тип не найден).

## 5. Известные ограничения (по состоянию на build 56)

- `DeviceBrowserService` — доступ к MTP-устройствам через Shell COM может
  требовать, чтобы устройство было разблокировано и в режиме "Передача
  файлов" (для Android) / доверия компьютеру (для iOS через iTunes/Apple
  Mobile Device Support).
- `SunsetToSunrise` без ручных координат зависит от IP-геолокации
  (`ip-api.com`) — точность на уровне города, не GPS.
- `AutoOffScheduler.SmartUsage` требует ~24 минут работы (6 семплов по 4
  мин) для накопления данных, прежде чем начнёт принимать решения — до
  этого считает рамку активной.
- **Live Tiles реально работают только под MSIX-установкой** — это
  ограничение самой Windows (package identity), не что-то, что можно
  доработать на уровне кода ClickOnce/InnoSetup-сборки. См. `Package/
  README_MSIX.md`.
- На `TileSmall` (71×71) Windows на части версий всё равно показывает
  только значок приложения вместо кадра фото, независимо от XML плитки —
  так исторически устроен этот конкретный размер в самой ОС.
- Один `.msix`/один `Package.appxmanifest` описывает ОДНУ архитектуру
  (`ProcessorArchitecture`) за раз — сборка `.msixbundle` с несколькими
  архитектурами не автоматизирована в этом репозитории (см. `Package/
  README_MSIX.md`, раздел про `makeappx bundle`).
- `SldInterval` (основной интервал слайдшоу) в Настройках остался
  read-only лейблом, не парой Slider+TextBox — формат отображения
  "1м 30с" не однозначно разбирается обратно при наборе текста, а на
  главном экране для этого значения уже есть отдельные крупные
  touch-кнопки +/- на тулбаре.
- Таймаут блокирующих COM-вызовов в `DeviceBrowserService`
  (`RunBlocking<T>`, 15 с) не отменяет сам зависший вызов — позднее
  связывание COM не поддерживает отмену на уровне ОС. Управление
  возвращается вызывающей стороне, но фоновый поток может продолжать
  ждать до тех пор, пока вызов сам не завершится (или никогда, если
  устройство не отвечает вовсе) — на UX это не влияет, но стоит иметь в
  виду при диагностике зависших потоков в отладчике.
- Ни одно из изменений build 55/56 (MSIX-упаковка, обновления) не было
  прогнано через реальную сборку (`dotnet build`/`msbuild`/`iscc`/
  `makeappx`) — в песочнице, где выполнялась работа, нет .NET SDK и
  Windows-инструментов. Проверено статически (баланс скобок, валидность
  XML/YAML, перекрёстные ссылки между `.xaml`/`.xaml.cs`) — см. `AUDIT.md`.
  Соберите и запустите в VS2026 перед публикацией.
